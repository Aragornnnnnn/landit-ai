# LAN-373 작업 0 스파이크 결과 — 억양 판정 방식 확정

계획의 선행 스파이크(억양별 판정 검증) 결과다. 결론은 **억양 판정을 일반 대조 판정에서
분리해 단어 단위 양자택일 질문으로 수행한다**이다.

## 1. OpenRouter TTS 호출 형태 — 검증 완료

계획이 최대 리스크로 잡았던 항목이다. 3 locale 모두 정상 생성됐다.

```python
client.audio.speech.create(model=..., voice=..., input=..., response_format="mp3")
```

| locale | 모델 | 음성 | 결과 |
| --- | --- | --- | --- |
| EN_US | `microsoft/mai-voice-2` | `en-US-Harper:MAI-Voice-2` | OK (53.8KB) |
| EN_GB | `deepgram/aura-2` | `aura-2-draco-en` | OK (15.3KB) |
| EN_AU | `deepgram/aura-2` | `aura-2-hyperion-en` | OK (14.5KB) |

## 2. 열린 질문으로 억양을 물으면 환각이 터진다 — no-go

대조 프롬프트에서 "minor accent coloration 무시" 문구를 빼고 학습 억양을 기준으로
판정하게 했다. 문장 3개 × 참조 3 locale × 화자 3 locale = 27 케이스.

| 항목 | 억양 무시(PoC 검증본) | 억양 기준 |
| --- | --- | --- |
| 같은 억양 오탐 | 3/11 (27%) | **6/9 (67%)** |

- `schedule` 8/9, `tomato` 8/9, `advertisement` 9/9로 **미/영 차이로 유명한 단어만**
  두 오디오의 실제 차이와 무관하게 지적했다.
- 문장에 없는 단어(`wash`)를 지어낸 응답이 나왔다. 실제 문장은 "I can't **watch** ..."다.
- 같은 케이스에서 `advertisement`가 SOUND와 STRESS로 번갈아 분류됐다.

LAN-209가 이미 탈락시킨 환각 모드(*"실제 청지각이 아니라 사전 지식 기반 환각"*)가
억양 축에서 그대로 재현된 것이다.

## 3. 테스트 데이터 결함도 함께 확인됐다

`schedule`을 양자택일로 물었더니 **6개 오디오 전부 "sk"**였다. 영국·호주 참조 음성도
`skedule`이라고 발음한다. 즉 2절의 `schedule` 지적 8/9는 존재하지 않는 차이를 지적한
것이다.

TTS 억양 재현은 두 층위로 갈린다.

- **음성적 특징**(flap T, 비rhotic r, BATH 모음): 억양 모델에 규칙으로 들어 있어 재현된다.
  `water`는 US→`wah-der`, GB/AU→`waw-tuh`로 정확히 갈렸다.
- **어휘적 차이**(`schedule`, `tomato`, `vitamin`): 단어별 사전 항목이라 음성에 따라
  재현되지 않을 수 있다. `aura-2 draco`는 영국 음성인데도 `skedule`을 낸다.

### 정정 (2026-08-26): 음성 문제였지 TTS 일반의 한계가 아니다

발음 학습용 음성을 캐릭터 음성과 분리하면서(아래 참조) 여성 음성으로 다시 측정한 결과
**어휘적 차이도 정확히 재현됐다.**

| 단어 | EN_US `thalia` | EN_GB `pandora` | EN_AU `theia` |
| --- | --- | --- | --- |
| schedule | skedule | **shedule** | **shedule** |
| water | wah-der | waw-tuh | waw-tuh |
| tomato | tuh-MAY-toh | tuh-MAH-toh | tuh-MAH-toh |

9/9 전부 기대한 억양대로 나왔다. 즉 `draco` 하나의 결과로 "TTS는 어휘적 차이를 재현하지
못한다"고 일반화한 것은 잘못이었다. **음성 선택의 문제**이며, 새 음성 구성에서는 억양
판정의 전제조건(참조 음성이 locale별로 실제 다른 발음을 낼 것)이 충족된다.

## 발음 학습용 음성 구성 (2026-08-26 확정)

시나리오 캐릭터 음성과의 충돌을 피하고 유저 구성(95% 여성)에 맞춰 **억양별 여성 음성**을
따로 배정한다. 캐릭터 음성은 `chloe: luna`, `marco: hyperion`, `teddy: draco`이므로
아래 셋과 겹치지 않는다.

| locale | 음성 | 비고 |
| --- | --- | --- |
| EN_US | `aura-2-thalia-en` | 미국 여성 |
| EN_GB | `aura-2-pandora-en` | aura-2의 유일한 영국 여성 |
| EN_AU | `aura-2-theia-en` | aura-2의 유일한 호주 여성 |

- 모델은 `deepgram/aura-2`로 통일한다 (시나리오 파이프라인과 동일).
- **속도 조절은 하지 않는다.** `speed` 파라미터는 동작하지만(aura-2는 0.85에서 약 25%
  느려지며 값에 비례한다) 기본 속도를 쓰기로 했다.

### TTS 생성은 어휘 선택에서 비결정적이다 — 생성물 검증이 필요하다

같은 음성으로 여러 번 생성해 `tomato`를 확인한 결과다.

| 음성 | 결과 |
| --- | --- |
| `thalia` | MAY 3/3 (미국식) |
| `cordelia` | MAH 1회, MAY 2회 |
| `asteria` | MAH 1회, MAY 1회 |

**특정 음성의 결함이 아니라 생성마다 어휘 선택이 흔들리는 것이다.** 파이프라인이 한 번
생성한 결과를 S3에 `immutable` + 1년 캐시로 게시하므로, 운 나쁜 한 번이 그대로 콘텐츠로
굳는다. 미국 학습자에게 1년간 `tuh-MAH-toh`를 들려줄 수 있다.

→ **작업 3 요구사항**: 기존 파이프라인의 MP3 검증(재생 가능 여부·길이)에 더해,
**억양 대조 단어가 기대한 발음으로 생성됐는지 업로드 전에 확인**한다. 검사 수단은
4절의 양자택일 질문을 그대로 쓴다. 어긋나면 재생성하고, 반복 실패하면 사람이 확인한다.

## 4. 좁은 양자택일은 작동한다 — go

같은 모델·오디오·설정에서 질문 형태만 바꿨다. 열린 질문("차이를 찾아라") 대신
선택지를 주고 고르게 했다.

사람 녹음(문장 3개 × 미국식/영국식 2벌) 기준 **11/12 정확**.

| 단어 | 대조 | 미국식 녹음 | 영국식 녹음 |
| --- | --- | --- | --- |
| schedule | sk / sh | O | O |
| water (문장 a) | flap / clear t | O | O |
| can't | KANT / KAHNT | O | O |
| tomato | MAY / MAH | O | O |
| advertisement | 3음절 / 2음절 강세 | O | O |
| water (문장 c) | flap / clear t | **X** | O |

- 열린 질문에서 8/9 환각이던 `schedule`을 2/2 정확히 판별했다.
- 강세 대조(`advertisement`)도 2/2 맞혔다.
- 유일한 오답은 문장 c의 미국식 `water`를 `wah-tuh`로 들은 것이다. 같은 단어를 문장 a에서는
  맞혔으므로 녹음의 flap이 약했을 가능성이 있다. **확인 필요**.

## 확정 구조

판정을 두 갈래로 분리한다.

1. **일반 발음·강세 판정** — PoC 검증본(억양 중립) 대조 프롬프트를 그대로 유지한다.
   24/24·오탐 0이라는 실측 근거가 있는 유일한 자산이므로 건드리지 않는다.
2. **억양 판정** — 문장의 억양 대조 단어에만 양자택일 질문을 병렬로 던진다.
   문장이 고정 콘텐츠이므로 대조 정의를 사전 생성해 BE가 요청에 실어 보낸다.

```json
{ "order": 8, "word": "water",
  "accentContrast": { "expected": "a clear t (WAW-tuh)",
                      "other": "a d-like flap (WAH-der)",
                      "errorType": "PHONEME" } }
```

본 판정이 이미 오류로 본 단어는 억양 판정이 덮어쓰지 않는다. 억양 확인 호출이 실패하거나
판별이 불확실하면 해당 단어는 판정에서 제외해 본 판정 결과를 그대로 반환한다.

## 부수적으로 발견·수정한 결함

- **스키마 위반이 재시도되지 않던 문제**: 36회 중 1회 발생. JSON 파싱 실패만 재시도하고
  스키마 위반은 그대로 502로 흘렸다. 같은 재시도로 흡수하도록 수정했다.
- **프롬프트 렌더링 실패**: 프롬프트 본문의 JSON 예시 중괄호를 `str.format`이 플레이스홀더로
  해석해 27회 호출이 전부 실패했다. `str.replace`로 바꾸고, 프롬프트를 실제로 렌더링하는
  테스트를 추가했다. 기존 테스트가 전부 mock이라 프롬프트 문자열이 한 번도 만들어지지
  않았던 것이 원인이다.

## 5. 골든 셋 회귀와 판정 안정성

확장 필드를 대조 프롬프트에 직접 요구한 판과 PoC 검증본을 A/B로 비교했다.

| 실행 | 프롬프트 | 정확일치 | 오탐 | p50 |
| --- | --- | --- | --- | --- |
| 1 | 확장 | 22/24 | 2 run (`diner`) | 4.7s |
| 2 | 검증본 | **24/24** | **0** | 4.2s |
| 3 | 검증본 | 22/24 | 2 run (`diner`) | 4.1s |

**같은 프롬프트(검증본)로 돌린 2회차와 3회차의 결과가 다르다.** 즉 `diner` 오탐은
확장 필드 탓이 아니라 **회차 간 변동**이다. temperature 0이지만 reasoning 모델이라
실행마다 결과가 흔들린다.

이 사실이 남기는 것:

- A/B를 각 1회씩만 돌려 원인을 단정하면 안 된다. 위 표의 1↔2 비교만 봤을 때는
  "확장 필드가 오탐을 만든다"는 잘못된 결론이 나온다.
- PoC가 기록한 "24/24, 오탐 0"도 샘플당 2회 기준이므로 **오탐률의 신뢰구간을 주기에는
  회차가 부족하다.** 기준선 자체를 회차를 늘려 다시 재야 한다.
- `s2_correct`(*"I can't wait to try a real American diner."*)가 반복해서 흔들리는
  샘플이다. LAN-209에서도 화자 2의 `can't` 반복 지적을 "화자의 실제 발음 특성일 가능성"으로
  남겨뒀는데, 같은 문장이다. 샘플 자체를 의심해볼 필요가 있다.

지연은 세 실행 모두 p50 4.1~4.7초로 목표(5초) 안에 들어왔다.

## 확정한 판정 구조 — 질문을 셋으로 쪼갠다

억양(2·4절)과 확장 필드(5절)에서 같은 교훈이 반복됐다. **이 모델은 한 번의 열린 판단에
여러 요구를 얹으면 무너지고, 좁은 단일 질문으로 나누면 잘한다.** 그래서 호출을 셋으로 나눴다.

| 호출 | 역할 | 모듈 |
| --- | --- | --- |
| 탐지 | 오류 단어·유형 판정 (PoC 검증본 그대로) | `llm/compare.py` |
| 묘사 | respelling·오류 구간·강세 위치 | `llm/describe.py` |
| 억양 | 대조 단어 양자택일 | `llm/accent_check.py` |

묘사·억양 호출은 탐지 결과를 바꿀 수 없다. 묘사는 이미 오류로 확정된 단어에만 붙고,
억양은 탐지가 CORRECT로 본 단어에만 적용한다. 오류가 없으면 묘사 호출은 발생하지 않는다.

## 남은 확인 사항

- **오탐률 재측정**: 회차를 늘려(5회 이상) 분포를 봐야 한다. 2회로는 판정 불가.
- **`s2_correct` 샘플 검토**: 반복해서 흔들리는 유일한 샘플이다. 녹음 자체를 확인한다.
- 문장 c 미국식 `water` 오답은 **모델 오답으로 확정**됐다. 녹음에 flap이 정상적으로
  들어가 있음을 기획자가 확인했다. 양자택일 정확도는 11/12(92%)로 기록한다.
  같은 단어를 문장 a(중간 위치)에서는 맞히고 c(끝 위치)에서는 틀렸으므로,
  **대조 단어의 문장 내 위치에 따른 정확도 차이**를 확인해볼 값어치가 있다.
- EN_AU는 사람 녹음이 없어 미검증이다. TTS 의사-화자에서는 `water` 대조가 정확했다.
- 묘사 호출을 분리한 뒤의 품질은 아직 실제 오디오로 측정하지 않았다.
