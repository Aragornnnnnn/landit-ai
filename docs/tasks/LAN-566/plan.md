# LAN-566 기억 생성의 시간·토큰 예산과 재시도 정책 개선

## 근거와 범위

- `origin/main`의 `8ba7010`에서 `hotfix/LAN-566`을 생성했다. 기존 작업 공간의 변경은 보존한다.
- 2026-09-25 세션 6852는 사용자 확인 자료 기준 최초·재시도 모두 completion 4096, reasoning 4096, 답변 0, `length/max_output_tokens`였다. BE 58.547초만으로 timeout으로 분류하지 않는다.
- AI-PROD-G와 BE-PROD-M은 같은 요청이다. 과거 약 60초 실패 2건의 원인은 미확정이며 중복 대체 교정은 기존 구현을 유지한다.
- 과거 작업 재처리, 검색 시점, 레벨 평가, 모델 변경, queue 도입은 제외한다.

## 결정

| 경로 | AI 전체 외부 호출 예산 | BE HTTP 제한 | 실제 HTTP 호출 상한 |
| --- | ---: | ---: | ---: |
| 후보 추출·검수·임베딩·후속 질문 | 공유 50초 | 55초 | 9회 |
| 판정·중복 대체 교정 | 공유 20초 | 25초 | 7회 |

- 기존 BE 60초보다 먼저 AI가 실패를 반환하도록 후보 전체에 50초를 배정하고 전송 여유 5초를 둔다. 판정은 검수·임베딩이 없는 별도 요청이므로 20초로 제한한다. 성능 최적값을 실측한 값이 아니라 대기 시간의 운영 상한이다.
- 각 provider 호출은 `min(20초, 전체 잔여 시간, 호출별 timeout)`이다. 후속 질문의 기존 10초도 유지한다. SDK 자동 재시도는 0회이며 모든 재호출은 같은 deadline을 사용한다.
- 동기 SDK는 유지하되 기억 요청의 HTTP 전송만 취소 가능한 비동기 송수신으로 감싼다. 본문이 조금씩 도착해도 전체 deadline은 늘어나지 않는다. 요청 종료 시 ContextVar를 복원하며 세션 상태를 보관하지 않는다.
- 후보의 9회는 추출 최대 4회 + 검수 1회 + 임베딩 1회 + 후속 질문 최대 3회다. 판정의 7회는 최초 최대 4회 + 중복 교정 최대 3회다. 형식 미지원 시 전환도 횟수·시간에 포함한다. timeout은 형식 미지원으로 처리하지 않는다.
- 추출·검수는 `medium → low`, 전체 생성 한도는 4096을 유지한다. 판정·기억 생성 중 후속 질문도 4096 상한을 적용한다. low가 일정한 추론 토큰 수나 답변 공간을 보장하지는 않는다.
- `length` 또는 native `max_output_tokens/max_tokens`이면 내용이 비었거나 JSON이 완성돼 있어도 실패시킨다. 같은 조건의 재시도는 하지 않는다. 일반 빈 응답·JSON 오류는 기존 재시도 상한을 유지한다.
- 형식 미지원 fallback과 원문 근거·후보 인덱스·중복 대체 정합성 검증은 유지한다. 빈 응답은 후보 0개로 바꾸지 않는다. 정상적인 `candidates: []`는 성공이다.
- 요청별 시도 순서, 소요 시간, 종료 사유, completion/reasoning 토큰, provider ID, 최초 실패 코드를 로그에 남긴다. 응답 본문·prompt·exception 문자열은 복사하지 않으며 ID 형식과 종료 사유는 허용 목록으로 제한한다. 제공되지 않은 정보는 null이다.
- 정책 구분을 위해 extractorVersion은 `memory-candidate-v11`로 올린다. DTO/OpenAPI 계약은 변경하지 않는다.

## 검증과 한계

- 먼저 `length` 재시도·진단 누락을 재현했다. 기존 코드는 한도 소진을 무시했고 최초 실패 이유가 보존되지 않았다.
- 로컬 HTTP 서버로 개별 제한, 연속 호출의 공유 예산, 느린 본문, SDK 재시도 0회, 호출 상한, 압축 응답을 검사한다.
- 기존 후보 검수·중복 대체 교정 테스트와 전체 unittest를 실행한다. 최종 실행 결과는 아래에 기록한다.
- BE의 실패 시 저장 제외·대화 완료 유지, 일반 timeout 유지와 전체 check는 BE 작업 문서에 기록한다.
- deadline은 외부 I/O에 적용된다. 동기 DTO 검증·JSON 직렬화와 ASGI 작업 스레드 대기 시간을 선점하지 않는다. 두 endpoint 사이의 BE DB 처리 시간도 별도다.
- provider가 이미 시작한 연산·과금까지 취소된다는 보장은 없다. 한도 소진 시 두 번째 4096-token 호출을 없애지만 평균 비용·지연 개선은 운영에서 측정해야 한다.
- 테스트는 합성 응답·mock 및 로컬 HTTP 검증이다. 실제 LLM의 추출 품질과 운영 성공률 개선은 검증하지 않았다. low의 품질 저하 가능성은 배포 전 별도 표본 평가가 필요하다.
- OpenRouter의 [추론 토큰 정책](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)에 따르면 추론과 답변은 생성 한도를 공유하며 `exclude`는 추론을 숨길 뿐 한도 소모를 제거하지 않는다.
